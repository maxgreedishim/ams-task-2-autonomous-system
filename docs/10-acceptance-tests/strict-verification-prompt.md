# Промт строгой проверки проекта

Ты проверяешь проект в workspace:

```text
/Users/max/ams-task-2-autonomous-system
```

Главный источник требований:

```text
/Users/max/Downloads/AMS_задание_2_автономная_система.pdf
```

Проверяй только направление B — «Управляемые действия».

## Правила проверки

1. Сначала прочитай PDF полностью, затем README и документацию
   из `docs/`.
2. Считай PDF главным источником требований.
3. Сравни PDF, документацию и фактический код.
4. Не объявляй требование выполненным только по наличию файла или теста.
5. Для каждого требования выполни реальную проверку и зафиксируй
   результат.
6. Не добавляй фиктивные проверки и не ослабляй policy ради прохождения
   теста.
7. Если найдёшь дефект, исправь его и повтори полный прогон.
8. После каждого изменения обязательно запускай проверку TypeScript.
9. В итоговом отчёте разделяй `PASS`, `FAIL`, `PARTIAL`, `BONUS` и `N/A`.
10. Все расхождения между PDF, документацией и кодом укажи отдельно.

## Проверка Docker с первого запуска

Не запускай проект сначала через `npm run dev`. Основной сценарий
проверки Docker — штатный shell-скрипт:

```bash
cd /Users/max/ams-task-2-autonomous-system
bash -n run-docker.sh
./run-docker.sh
```

Проверь:

- скрипт запускается из чистого состояния;
- файл имеет права на выполнение;
- скрипт сам обрабатывает старые контейнеры этого проекта;
- чужие Compose-проекты не останавливаются;
- зависимости устанавливаются внутри контейнеров;
- server и client стартуют без ручного вмешательства;
- скрипт выводит фактические URL;
- при свободных портах используются `3000` и `4000`;
- при занятых портах скрипт явно сообщает фактические порты;
- API health отвечает успешным статусом;
- UI отвечает успешным HTTP-статусом;
- `NEXT_PUBLIC_API_URL` указывает на фактический API-порт;
- ошибки первого запуска диагностируются по логам контейнеров.

Проверка должна использовать `./run-docker.sh`, а не подменять его
ручным `docker compose up`.

После запуска выполни:

```bash
docker compose -p ams-task-2-autonomous-system ps -a
curl -i http://localhost:4000/health
curl -I http://localhost:3000/
```

Если скрипт выбрал другие порты, используй их из вывода и зафиксируй
причину.

## Статические проверки

Запускай команды последовательно, чтобы сборки Next.js не конфликтовали
между собой:

```bash
npm run fsd:check
npm run typecheck
npm run lint
npm test
docker compose config
```

Проверь TypeScript отдельно для client и server, если это нужно для
диагностики.

### FSD

Проверь строгое соответствие FSD и структуре Next.js:

- маршруты Next.js находятся в `client/app`;
- FSD-слои находятся в `client/src`;
- используются слои `_app`, `_pages`, `widgets`, `features`, `entities`, `shared`;
- импорты идут только от нижнего слоя к верхнему;
- нет импорта из `entities` в `features`, `widgets` или `_pages`;
- нет импорта из `features` в `widgets` или `_pages`;
- нет импорта из `widgets` в `_pages` через обратное направление;
- между слайсами используются публичные API;
- отсутствуют deep imports через внутренние файлы чужого слайса;
- используются алиасы `@/...`, а не относительные cross-layer пути;
- публичные `index.ts` экспортируют только разрешённый API;
- FSD-проверка анализирует исходные файлы, а не только наличие
  каталогов.

## Ровно три автоматических теста

Проверь, что обязательный набор содержит ровно три теста:

1. Основной сценарий:
   задача проходит состояния и формирует результат.
2. Безопасный отказ:
   запрещённая запись, неизвестный инструмент или недопустимые аргументы
   останавливаются до выполнения.
3. Защита от дубля:
   повторная отправка `task_id` и повторное подтверждение не создают
   вторую задачу или второе действие.

Для каждого теста укажи имя, файл, входные данные и эффект.

## Фактическая проверка API направления B

Создай задачи через Docker API и проверь:

```text
GET  /health
POST /tasks
GET  /tasks/{task_id}
GET  /tasks/{task_id}/events
POST /tasks/{task_id}/confirm
POST /tasks/{task_id}/cancel
```

Проверь HTTP-коды, тело ответа, состояние задачи, `task_id`, `trace_id`,
plan, result, limits и audit-события.

## Обязательные runtime-сценарии направления B

### 1. Только чтение

- создай задачу в `read_only`;
- разреши `list_records` и `get_record`;
- проверь, что `create_followup` блокируется до gateway;
- проверь отсутствие записи в mock-системе;
- проверь audit с причиной блокировки.

### 2. Подтверждение

- создай задачу в `confirm`;
- проверь статус `WAITING_CONFIRMATION`;
- проверь видимость точного инструмента и аргументов;
- подтверди задачу;
- проверь выполнение записи и статус завершения;
- повтори подтверждение;
- проверь отсутствие второго действия.

### 3. Повторная отправка

- отправь тот же `task_id` повторно;
- проверь возврат существующей задачи;
- проверь отсутствие второй задачи и лишних событий.

### 4. Неизвестный инструмент

- передай или внедри неизвестный tool в план;
- проверь отказ policy/gateway до исполнения;
- проверь отсутствие вызова mock-инструмента.

### 5. Workspace boundary

- запроси запись другого workspace;
- попробуй изменить запись другого workspace;
- проверь отказ и отсутствие утечки данных.

### 6. Поля `get_record`

- запроси допустимые поля `title`, `status`, `owner`;
- запроси недопустимое поле;
- проверь отказ до вызова инструмента.

### 7. Недоверенный output

- верни из инструмента текст с инструкцией изменить policy;
- проверь, что текст считается данными;
- проверь, что policy и gateway не изменились.

### 8. Лимиты

Проверь фактическое ограничение каждого параметра:

- `max_steps`;
- `max_tool_calls`;
- `max_runtime_seconds`.

### 9. Отмена

- создай активную задачу;
- вызови cancel;
- проверь `CANCELLED`;
- подтверди отменённую задачу;
- проверь, что она не стала `COMPLETED`.

### 10. Перезапуск

- создай задачу и получи audit;
- перезапусти server-контейнер;
- снова запроси задачу и события;
- проверь сохранность состояния и audit.

## Проверка реактивного frontend

Без перезагрузки страницы проверь:

- создание новой задачи заменяет старую карточку;
- режим и статус обновляются сразу;
- план и аргументы появляются сразу;
- подтверждение меняет статус и результат;
- audit загружается автоматически;
- повторное подтверждение не создаёт второе действие;
- после `read_only` отображается понятный безопасный отказ;
- не остаётся данных предыдущей задачи.

Проверь интерфейс на viewport, близком к MacBook 13.3″:

- вся основная информация помещается в viewport;
- нет прокрутки страницы;
- нет обязательной прокрутки внутренних блоков;
- длинные UUID отображаются без разрушения layout;
- текст не перекрывается и не обрезается.
